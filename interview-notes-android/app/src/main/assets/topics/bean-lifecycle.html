2. The Fundamentals

2.1 What the container really is HIGH

What: ApplicationContext wraps a DefaultListableBeanFactory: essentially a Map<String, BeanDefinition> (recipes) plus a Map<String, Object> singleton cache (cooked beans). A BeanDefinition is metadata: class, scope, constructor args, dependencies, init/destroy methods, lazy flag. Why: separating recipe registration from instantiation lets Spring post-process definitions (e.g. property placeholders) before any object exists, and lets it order creation by dependency graph.

The container is two maps — BeanDefinitions (recipes) and the singleton cache (instances) — and refresh() turns one into the other in dependency order.

2.2 Bootstrap order inside refresh() know it

1) Component scanning / config-class parsing registers BeanDefinitions. 2) BeanFactoryPostProcessors run — they edit definitions before beans exist (this is how @Value placeholders and @ConfigurationProperties binding infrastructure get wired). 3) BeanPostProcessors are instantiated first (they must exist to process everyone else). 4) All non-lazy singletons are eagerly created via preInstantiateSingletons().

BeanFactoryPostProcessors mutate recipes; BeanPostProcessors mutate instances — and that ordering is why post-processors themselves are created first.

2.3 The per-bean lifecycle — exact order HIGH

flowchart TD
    A[Constructor runs - constructor injection happens here]:::high --> B[Dependency injection: Autowired fields / setters]:::high
    B --> C[BeanNameAware / BeanFactoryAware / ApplicationContextAware]
    C --> D[BPP postProcessBeforeInitialization]
    D --> E[PostConstruct method]:::high
    E --> F[InitializingBean.afterPropertiesSet]
    F --> G[Bean initMethod attribute]
    G --> H[BPP postProcessAfterInitialization - AOP proxy wrapping]:::high
    H --> I[In use]
    I --> J[PreDestroy]:::high
    J --> K[DisposableBean.destroy]
    K --> L[destroyMethod attribute]

Why three init hooks? History: afterPropertiesSet (interface, couples you to Spring), init-method (XML era, decoupled), @PostConstruct (JSR-250 standard — the one to use). All three can coexist; they run in the order above.

Key implication: in the constructor your @Autowired fields are still null (field injection happens after construction). Anything needing injected state goes in @PostConstruct — or better, use constructor injection so the object is never in a half-built state.

Order: constructor → injection → Aware → BPP-before → @PostConstruct → afterPropertiesSet → init-method → BPP-after (where proxies wrap) → ... → @PreDestroy on shutdown.

2.4 BeanPostProcessors — where the magic lives HIGH

What: an interface with two callbacks invoked around every bean's init phase. Nearly every "magic" annotation is a BPP: AutowiredAnnotationBeanPostProcessor (@Autowired/@Value), CommonAnnotationBeanPostProcessor (@PostConstruct/@PreDestroy), and AnnotationAwareAspectJAutoProxyCreator — which, in postProcessAfterInitialization, returns a proxy instead of your bean when advice applies (@Transactional, @Async, @Cacheable, security annotations).

Why after-init? The real object must be fully initialized before being wrapped; the container then caches and injects the proxy, so every other bean talks through the interceptor chain.

Spring's annotation magic is just BeanPostProcessors — and AOP is one that swaps your fully-initialized bean for a proxy in postProcessAfterInitialization, which is exactly why self-invocation bypasses advice.

2.5 Proxy mechanics: JDK vs CGLIB HIGH

JDK dynamic proxy: implements the bean's interfaces via java.lang.reflect.Proxy — only interface methods are advised. CGLIB: generates a runtime subclass — so the class and advised methods can't be final, and the proxy calls through to the target. Spring Boot defaults to CGLIB even when interfaces exist (proxyTargetClass=true), for consistent injection by concrete type.

JDK proxies implement interfaces, CGLIB subclasses the class (so no final methods); Boot defaults to CGLIB so beans can always be injected by their concrete type.

2.6 Scopes know it

singleton (default): one instance per container (not per JVM — that's the trap), cached eagerly. prototype: new instance per getBean(); Spring does NOT call destroy callbacks on prototypes (it doesn't track them after handing them over). Web scopes: request, session, application, websocket. Injecting a shorter-lived scope into a singleton needs a scoped proxy (proxyMode = TARGET_CLASS) or ObjectProvider — otherwise the singleton freezes one instance at startup.

Singleton means one per container; prototypes get no destroy callbacks; and injecting request/prototype beans into singletons requires a scoped proxy or ObjectProvider, or you've frozen the first instance forever.

2.7 Circular dependencies — the three-level cache HIGH

Mechanism: while creating A, Spring puts a factory for the early reference of A into cache level 3 (singletonFactories) right after instantiation, before population. When B (needed by A) asks for A, it receives that early half-initialized reference (promoted to level 2, earlySingletonObjects), letting the cycle close; finished beans land in level 1 (singletonObjects). Why a factory and not the raw object? So AOP can hand out the proxy early if needed.

Limits: works only for singleton, field/setter-injected cycles. Constructor-injection cycles can never work — you can't expose an early reference before the constructor finishes. Spring Boot 2.6+ rejects all circular refs by default (spring.main.allow-circular-references=false); the real fix is redesign, or @Lazy on one edge.

Spring closes setter/field cycles by exposing an early reference from the three-level singleton cache; constructor cycles are unsolvable, and since Boot 2.6 all cycles are rejected by default — the fix is redesign or @Lazy, not the flag.

3. Clean Code Examples

3.1 Constructor injection (idiomatic) vs field injection

Idiomatic (Boot 3) 
@Service
public class InvoiceService {
    private final InvoiceRepo repo;      // final = fully built after ctor

    public InvoiceService(InvoiceRepo repo) {  // single ctor: @Autowired implicit
        this.repo = repo;
    }
}
Common wrong way 
@Service
public class InvoiceService {
    @Autowired private InvoiceRepo repo;      // field injection

    public InvoiceService() {
        // repo.count();  → NullPointerException: injection hasn't run yet
    }
}

Why it fails / is worse: fields are injected reflectively after the constructor, so the object has a half-built window; it can't be final, hides dependencies, and is untestable without a container or reflection tricks.

3.2 Lifecycle callbacks

Idiomatic 
@Component
public class CacheWarmer {
    private final ProductRepo repo;
    private Map<Long, Product> cache;

    CacheWarmer(ProductRepo repo) { this.repo = repo; }

    @PostConstruct               // jakarta.annotation.PostConstruct in Boot 3
    void warm() { cache = repo.loadHot(); }   // deps are injected by now

    @PreDestroy
    void flush() { cache.clear(); }
}
// Startup log order proof: ctor → @PostConstruct → (BPP-after/proxy) → ready
Common wrong way 
CacheWarmer(ProductRepo repo) {
    this.repo = repo;
    warm();               // works here, BUT:
    selfProxyMethod();    // any call relying on AOP (@Async, @Cacheable,
}                          // @Transactional) runs UNPROXIED — proxy doesn't exist yet

Why it fails: during construction (and even @PostConstruct) the AOP proxy hasn't wrapped the bean yet — annotations on your own methods are silently ignored. Also with field injection, doing work in the constructor NPEs.

3.3 Prototype into singleton

Idiomatic 
@Component @Scope("prototype")
class ReportBuilder { /* stateful, per-use */ }

@Service
class ReportService {
    private final ObjectProvider<ReportBuilder> builders;
    ReportService(ObjectProvider<ReportBuilder> builders) { this.builders = builders; }

    String run() { return builders.getObject().build(); }  // fresh instance per call
}
Common wrong way 
@Service
class ReportService {
    @Autowired ReportBuilder builder;   // injected ONCE at startup
    String run() { return builder.build(); }  // same "prototype" reused forever
}

Why it fails: injection happens once when the singleton is built; the prototype scope only governs getBean() calls, so you've effectively demoted it to a shared, non-thread-safe singleton.

3.4 A minimal BeanPostProcessor (know how the trick is done)

Idiomatic 
@Component
public class TimingBpp implements BeanPostProcessor {
    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        if (name.equals("invoiceService")) {
            System.out.println("Wrapping " + name);   // this is where Spring
            // return a proxy here and callers get the proxy, not the bean
        }
        return bean;
    }
}

Expected startup output: Wrapping invoiceService — once, after that bean's init callbacks.

4. Tricks, Tips & Rules of Thumb

  • Mnemonic "CIA-PIP" for the order: Constructor → Injection → Aware → PostConstruct (with BPP-before just ahead) → InitializingBean/init-method → Proxy (BPP-after).
  • Golden rule: constructor injection + final fields everywhere; @PostConstruct only for work that needs the container (warmups, validation).
  • Never rely on AOP annotations from inside the same class — proxy-based advice needs an external call. (Full story in the Transactions note.)
  • @Bean vs @Component: @Bean = you construct it in a @Configuration method (for third-party classes); @Component = Spring constructs it via scanning. Inside a proper @Configuration class, @Bean-method calls are CGLIB-intercepted so calling dataSource() twice returns the same singleton — but with proxyBeanMethods=false (or "lite" @Bean in a @Component) each call makes a new object.
  • Startup slow? @Lazy defers creation to first use; but eager-by-default is a feature — it fails fast at deploy, not at 2 a.m. on first request.
  • Version gotchas: Boot 3 = Spring 6 = jakarta.* — @PostConstruct is jakarta.annotation.PostConstruct (javax breaks silently: the annotation is simply ignored, no error). Boot 2.6+ bans circular refs by default. Spring 6 native/AOT builds the beans at build time — reflection-heavy tricks need hints.
  • Debug trick: a breakpoint in AbstractAutowireCapableBeanFactory#doCreateBean shows the whole lifecycle live; ctx.getBean(X.class).getClass() revealing $$SpringCGLIB$$ proves you hold a proxy.

    ↳ L1: Where exactly does the AOP proxy appear? (BPP postProcessAfterInitialization) ↳ L2: So what happens if @PostConstruct calls an @Async method on itself? (runs synchronously — no proxy yet, and self-call anyway)
  2. How does Spring resolve circular dependencies?
    ↳ L1: Why can't it work with constructor injection? (no object exists to expose early) ↳ L2: Why is level 3 a factory rather than the object? (so the early reference can be the AOP proxy when needed)

    ↳ L1: BFPP vs BPP? (definitions vs instances) ↳ L2: Why are BPPs instantiated before other beans, and what's the classic warning when a BPP depends on normal beans? ("bean X is not eligible for getting processed by all BeanPostProcessors" — those deps skip proxying)

    ↳ L1: What does @Configuration's CGLIB proxy guarantee? (inter-@Bean-method calls return the cached singleton) ↳ L2: Why would you set proxyBeanMethods=false? (faster startup/AOT friendliness when no @Bean method calls another)

6. Sticky-Note Summary

  • Container = BeanDefinition map + singleton cache; refresh() cooks recipes into beans.
  • Order: ctor → inject → Aware → BPP-before → @PostConstruct → afterPropertiesSet → init-method → BPP-after → use → @PreDestroy.
  • All annotation magic = BeanPostProcessors; AOP proxy wraps at BPP-after.
  • JDK proxy = interfaces; CGLIB = subclass (no finals); Boot defaults to CGLIB.
  • Constructor injection + final fields; @PostConstruct for container-dependent warmup only.
  • In the constructor, @Autowired fields are null. Always.
  • Circular deps: 3-level cache; setter/field-only; Boot 2.6+ rejects by default; fix = redesign or @Lazy.
  • Singleton = per container; prototype = per getBean(), no destroy callbacks; scoped proxy for narrow-into-wide injection.
  • Boot 3 = jakarta.annotation.* — a javax @PostConstruct is silently ignored.
  • getClass() shows $$SpringCGLIB$$? You're holding a proxy, not the bean.

Self-test (5 questions)

  1. In what order do these run: afterPropertiesSet, @PostConstruct, constructor, @Autowired field injection, postProcessAfterInitialization?
  2. Your @PostConstruct method calls this.cacheableMethod() annotated with @Cacheable. Is the cache used? Why?
  3. Beans A and B constructor-inject each other. What happens at startup and what are your two fixes?
  4. A prototype bean injected into a singleton behaves like a singleton. Explain the mechanism and the fix.
  5. What breaks when you copy Boot 2 code with javax.annotation.PostConstruct into a Boot 3 app — and how does the failure present?
Answers
  1. constructor → @Autowired field injection → @PostConstruct → afterPropertiesSet → postProcessAfterInitialization.
  2. No. Two reasons: the proxy may not exist yet at @PostConstruct time, and it's a self-invocation via this, which bypasses the proxy regardless.
  3. Startup fails with BeanCurrentlyInCreationException (unresolvable ctor cycle). Fixes: break the cycle by extracting the shared piece (best), or @Lazy one constructor parameter so a lazy proxy defers resolution.
  4. Injection resolved the prototype once while building the singleton. Fix: inject ObjectProvider<T> (or a @Lookup method / scoped proxy) and fetch per use.
  5. Nothing fails at startup — the annotation is simply not recognized, so the init method never runs; you discover it as missing initialization behavior at runtime. Boot 3 scans jakarta.annotation only.
