2. The Fundamentals

2.1 What @Transactional actually does HIGH

Mechanism: at startup a BeanPostProcessor wraps your bean in an AOP proxy. A call from outside hits TransactionInterceptor, which asks the PlatformTransactionManager (for JPA: JpaTransactionManager) to getTransaction(). That obtains a JDBC connection, sets autoCommit=false, and binds the connection to the current thread in a ThreadLocal (TransactionSynchronizationManager). Your repositories find that same bound connection — that's how multiple DAO calls join one transaction with zero passing-around. On normal return → commit; on qualifying exception → rollback; either way the connection is unbound and returned to the pool.

sequenceDiagram

@Transactional is an around-advice on a proxy: begin via the transaction manager, bind the connection to the thread so all repository calls share it, commit on return, rollback on unchecked exceptions.

2.2 The self-invocation trap HIGH

Why: the transaction lives in the proxy, and this is the raw target — an internal call this.methodB() never crosses the proxy, so methodB's @Transactional (or its REQUIRES_NEW) is silently ignored. Same reason private/final methods can't be advised: CGLIB overrides public/protected methods in a subclass; private ones aren't inherited, final ones can't be overridden.

Fixes, best first: move methodB to another bean; or inject your own proxy (ObjectProvider<Self> / self-autowire with @Lazy); avoid AopContext.currentProxy() except as a last resort (requires exposeProxy=true).

Self-invocation bypasses the proxy because 'this' is the raw object — so internal @Transactional/@Async/@Cacheable calls silently do nothing; the clean fix is moving the method to a collaborator.

2.3 Propagation — what happens at a tx boundary meeting another HIGH

  • REQUIRED (default): join the caller's tx, or start one. One physical tx → an inner failure marks the shared tx rollback-only.
  • REQUIRES_NEW: suspend the caller's tx (its connection is parked), acquire a second connection, run an independent tx. Use: audit logs / outbox rows that must survive the business rollback. Cost: two pooled connections held by one thread → pool-exhaustion deadlocks under load.
  • NESTED: JDBC savepoint inside the same tx — inner rollback rewinds to the savepoint, outer can continue. Works with JDBC/JdbcTemplate; JpaTransactionManager doesn't support savepoints for JPA — verify on your stack.
  • MANDATORY (throw if no tx), NEVER (throw if tx), SUPPORTS (join if present), NOT_SUPPORTED (suspend, run non-tx): assertion/utility semantics.
REQUIRED shares one physical transaction; REQUIRES_NEW suspends and opens a second connection — independent but a pool-deadlock risk; NESTED is a savepoint in the same transaction, and JPA generally doesn't support it.

2.4 Rollback rules HIGH

Default: rollback on RuntimeException and Error; checked exceptions COMMIT. Why: EJB heritage — checked exceptions were deemed "business outcomes", unchecked "bugs". Override per method: @Transactional(rollbackFor = Exception.class).

The rollback-only trap: with REQUIRED, if an inner advised method throws a RuntimeException, the interceptor marks the shared tx rollback-only even if the outer method catches the exception. The outer commit then throws UnexpectedRollbackException. Catching the exception does not un-mark the transaction.

Runtime exceptions roll back, checked exceptions commit by default — and once an inner advised method marks the shared transaction rollback-only, catching its exception outside can't save the commit; you get UnexpectedRollbackException.

2.5 Isolation levels — DB anomalies HIGH

LevelDirty readNon-repeatable readPhantomNote
READ_UNCOMMITTEDpossiblepossiblepossiblerarely used; Postgres treats as READ_COMMITTED
READ_COMMITTEDnopossiblepossibledefault in Postgres/Oracle
REPEATABLE_READnonopossible*default in MySQL/InnoDB (*InnoDB largely prevents phantoms via gap locks)
SERIALIZABLEnononofull ordering; retry on serialization failures

@Transactional(isolation = ...) sets it on the connection for that tx; DEFAULT means "whatever the DB defaults to" — so behavior differs between MySQL and Postgres with identical code. Isolation applies per-transaction, and only where a new tx starts (joining an existing tx keeps its isolation; Spring by default ignores the mismatch unless validation is enabled).

Isolation is enforced by the database, not Spring — Spring just sets it on the connection; DEFAULT inherits the vendor default, which is READ_COMMITTED on Postgres but REPEATABLE_READ on MySQL.

2.6 readOnly, timeout, and choosing managers know it

readOnly=true is a hint: Hibernate sets FlushMode.MANUAL (skips dirty-checking → real memory/CPU win, changes silently not saved), some drivers/routers use it to route to replicas. It is not a security boundary — writes may still succeed on some stacks. timeout caps seconds before the tx manager forces rollback on the next DB operation. Multiple datasources → one PlatformTransactionManager each, selected via @Transactional("otherTxManager"); spanning two DBs atomically needs JTA/XA or (usually better) the outbox pattern.

readOnly is an optimization hint — Hibernate stops dirty-checking — not an enforcement; and one @Transactional spans exactly one transaction manager, so two databases need JTA or an outbox design.

3. Clean Code Examples

3.1 Idiomatic service-layer transaction

Idiomatic (Boot 3) 
@Service
public class TransferService {
    private final AccountRepo accounts;
    TransferService(AccountRepo accounts) { this.accounts = accounts; }

    @Transactional   // org.springframework.transaction.annotation.Transactional
    public void transfer(long fromId, long toId, BigDecimal amt) {
        accounts.debit(fromId, amt);     // same thread-bound connection
        accounts.credit(toId, amt);      // both commit or both roll back
    }
}

Throw a RuntimeException between the two calls → the debit is rolled back. That's the whole point.

Common wrong way 
@Transactional
public void transfer(...) {
    try {
        accounts.debit(fromId, amt);
        accounts.credit(toId, amt);
    } catch (Exception e) {
        log.error("failed", e);      // swallowed → interceptor never sees it
    }                                 // → COMMITS the half-done debit
}

Why it fails: rollback is triggered by an exception propagating out through the proxy. Swallow it and the interceptor sees a normal return → commit. Log-and-rethrow, or use TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() if you must catch.

3.2 The self-invocation bug, concretely

Common wrong way 
@Service
public class OrderService {
    public void placeOrder(Order o) {     // NOT transactional
        validate(o);
        saveWithTx(o);                    // this.saveWithTx — bypasses proxy!
    }
    @Transactional
    public void saveWithTx(Order o) { /* runs with NO transaction */ }
}

Why it fails: the call never leaves the raw object, so the interceptor never runs; each repository call auto-commits individually. No error, no warning — just no atomicity.

Idiomatic fix 
@Service
public class OrderService {
    private final OrderPersister persister;   // separate bean = real proxy call
    OrderService(OrderPersister persister) { this.persister = persister; }
    public void placeOrder(Order o) { validate(o); persister.save(o); }
}

@Component
class OrderPersister {
    @Transactional
    public void save(Order o) { /* transactional for real */ }
}

3.3 REQUIRES_NEW for an audit trail

Idiomatic 
@Component
public class AuditWriter {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String event) {
        auditRepo.save(new Audit(event));   // commits even if caller rolls back
    }
}
// Caller: audit.record("attempted"); then business logic that may throw.
// Result: business rows rolled back, audit row committed.
Common wrong way 
@Transactional
public void process() {
    audit.record("attempted");   // audit ALSO @Transactional(REQUIRED)
    risky();                      // throws → everything rolls back,
}                                 // including the audit row you needed

Why it fails: REQUIRED joins the same physical tx — the audit write shares the caller's fate. (And beware: making it REQUIRES_NEW but calling it via this re-introduces the self-invocation bug.)

3.4 Checked exception commits — the silent one

Common wrong way 
@Transactional
public void importFile(Path p) throws IOException {
    repo.saveBatch(parse(p));
    archive(p);          // throws IOException (checked)
}                         // tx COMMITS the batch — checked = no rollback
Idiomatic 
@Transactional(rollbackFor = Exception.class)
public void importFile(Path p) throws IOException { ... }

Why the default exists: Spring inherited EJB's "checked exceptions are expected business outcomes" convention. Most teams standardize rollbackFor = Exception.class on anything that throws checked exceptions.

4. Tricks, Tips & Rules of Thumb

  • Mnemonic "RUN Commits Checked" — RUntime rolls back, Checked Commits. If a method throws checked exceptions, decide rollbackFor explicitly.
  • Put @Transactional on the service layer, on public methods, on classes Spring instantiates — never rely on it on private/final/internal-called methods. Annotate the concrete class (or the method), not just an interface, when using CGLIB.
  • Keep transactions short: no HTTP calls, no Kafka publish, no heavy computation inside a tx — you're holding a pooled connection and row locks the whole time. Fetch → compute → short tx to write.
  • @Transactional + @Async on the same method: the tx does not follow the thread — the async method needs its own @Transactional (ThreadLocal binding!).
  • Test trap: @Transactional on a @SpringBootTest rolls everything back after each test — great for isolation, but it can hide flush/constraint errors that only fire at commit; use TestEntityManager.flush() or @Commit when verifying real commit behavior.
  • Pool-deadlock rule of thumb: nesting REQUIRES_NEW under load needs pool size > concurrent-threads × connections-per-thread; otherwise all threads hold conn #1 waiting for conn #2.
  • Version gotchas: Boot 3/Spring 6: prefer Spring's @Transactional over jakarta.transaction.Transactional (Spring's has propagation/isolation/rollbackFor attributes). Boot auto-configures the right PlatformTransactionManager; you rarely define one. Hibernate 6 (Boot 3) changed flush/dirty-check details but not the model.
  • Debug trick: logging.level.org.springframework.transaction.interceptor=TRACE logs "Getting transaction for" / "Completing transaction for" — the fastest way to prove whether your method is actually advised.

Top 5 questions with follow-up chains

  1. How does @Transactional work internally?
    ↳ L1: How do two repositories share one transaction without passing a connection? (ThreadLocal binding via TransactionSynchronizationManager) ↳ L2: So what happens if you spawn a thread inside the method? (new thread has no bound tx — its DB work auto-commits separately)
  2. @Transactional on a private method — what happens?
    ↳ L1: Why exactly can't CGLIB advise it? (subclass can't override private/final) ↳ L2: How would you detect this in a running app? (tx interceptor TRACE logs / no proxy class on getClass())
  3. Difference between REQUIRES_NEW and NESTED?
    ↳ L1: Which one survives the outer rollback? (REQUIRES_NEW only — NESTED is inside the same tx) ↳ L2: Why is REQUIRES_NEW dangerous under load? (each thread holds two pooled connections → exhaustion deadlock)
  4. Outer method catches inner method's exception — does it commit?
    ↳ L1: Which condition makes the answer "no"? (inner method itself advised + REQUIRED → rollback-only flag on the shared tx) ↳ L2: And if the inner method was a plain unadvised call? (then catching works fine — no interceptor marked anything)
  5. When would you change the isolation level?
    ↳ L1: What anomaly does REPEATABLE_READ stop that READ_COMMITTED doesn't? (same row re-read changing mid-tx) ↳ L2: Why prefer optimistic locking (@Version) over SERIALIZABLE in a web app? (no long lock waits; conflicts detected at commit and retried — scales better for low contention)

6. Sticky-Note Summary

  • @Transactional = proxy around-advice; begin → thread-bound connection → commit/rollback.
  • Self-invocation, private, final ⇒ silently NOT transactional.
  • Default rollback: unchecked only. Checked commits. rollbackFor=Exception.class when in doubt.
  • Swallowing the exception inside the method ⇒ commit. Rollback needs the throw to reach the proxy.
  • Inner advised throw under REQUIRED ⇒ rollback-only ⇒ UnexpectedRollbackException even if caught outside.
  • REQUIRES_NEW = suspend + second connection (audit/outbox); pool-deadlock risk. NESTED = savepoint, same tx, not for JPA.
  • Isolation is the DB's job; Spring only sets it. Postgres default READ_COMMITTED, MySQL REPEATABLE_READ.
  • readOnly=true = no dirty-checking (perf), maybe replica routing — not write protection.
  • Keep tx short: no remote calls inside; you hold a connection + locks.
  • New thread = no transaction. @Async methods need their own.

Self-test (5 questions)

  1. A @Transactional method catches the DataAccessException from repo.save() and returns normally. The caller then gets UnexpectedRollbackException. Reconstruct exactly why.
  2. Method A (@Transactional) calls this.b() where b is @Transactional(REQUIRES_NEW). How many transactions run?
  3. Why does rollback happen for RuntimeException but not IOException by default, and how do you flip it?
  4. How do two repository calls in one service method end up on the same JDBC connection?
  5. Name two independent reasons an audit write inside a failing business method vanished, given AuditWriter.record was marked REQUIRES_NEW.
Answers
  1. repo.save() is itself advised (SimpleJpaRepository is @Transactional): the inner interceptor saw the RuntimeException and marked the shared REQUIRED tx rollback-only before the service caught it. At the outer commit, the tx manager finds the flag and throws UnexpectedRollbackException.
  2. One. The call via this never reaches the proxy, so REQUIRES_NEW is ignored; b runs inside A's transaction.
  3. EJB-inherited convention: checked = anticipated business outcome (commit), unchecked = bug (rollback). Flip with @Transactional(rollbackFor = IOException.class) — or noRollbackFor for the reverse.
  4. The transaction manager binds the connection to the thread in TransactionSynchronizationManager's ThreadLocal at tx start; DataSourceUtils/EntityManager lookups inside the same thread return the bound resource instead of a fresh pooled connection.
  5. (a) It was called through this/same class, so REQUIRES_NEW never engaged and it rolled back with the caller; (b) the audit call happened but its exception path/order meant it ran after the throw — i.e. it was never reached. (Also acceptable: record() threw and the new tx itself rolled back.)
