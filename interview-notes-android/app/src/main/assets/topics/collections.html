2. The Fundamentals

2.1 The hierarchy and why it exists context

What: Iterable → Collection → List/Set/Queue, and Map deliberately outside that tree (a Map is key→value, not a bag of elements). Why: interfaces separate contract (ordering? duplicates? random access?) from implementation (array, linked nodes, hash table, red-black tree). You pick a data structure by the contract you need and the big-O you can afford.

The collection interfaces encode contracts (ordering, uniqueness, access pattern); the implementations encode data-structure trade-offs — I choose by contract first, complexity second.

2.2 ArrayList vs LinkedList — the real mechanism HIGH

ArrayList is a resizable Object[]. Amortized O(1) append: when full it allocates a new array of ~1.5× capacity and copies (Arrays.copyOf). Random access is O(1) because it's pointer arithmetic on a contiguous array — CPU-cache friendly. Middle insert/delete is O(n) (System.arraycopy shift).

LinkedList is a doubly-linked node chain. O(1) insert/remove at a known node, but O(n) to find the node; every element is a separate heap object → pointer chasing, cache-hostile, ~3× memory per element.

In practice ArrayList wins almost always — even for inserts — because contiguous memory and cache locality beat LinkedList's theoretical O(1); I'd only reach for a Deque (ArrayDeque), not LinkedList.

2.3 HashMap internals — the interview centrepiece HIGH

What underneath: an array of buckets (Node[] table, default capacity 16, always a power of two). A put:

flowchart TD
    A[put key value] --> B[h = key.hashCode]
    B --> C[spread: h XOR h shifted right 16]
    C --> D[index = h AND capacity-1]
    D --> E{bucket empty?}
    E -- yes --> F[place new Node]
    E -- no --> G{same hash AND equals?}
    G -- yes --> H[replace value]
    G -- no --> I[append to chain]
    I --> J{chain length >= 8 and table >= 64?}
    J -- yes --> K[treeify to red-black tree O log n]
    J -- no --> L[stay linked list]
    F --> M{size > capacity * 0.75?}
    L --> M
    M -- yes --> N[resize: double capacity, redistribute]

    class C,D,K,N hot;
  • Why the XOR-shift ("spread")? Index uses only the low bits (h & (n-1)). Mixing the high 16 bits down protects against hashCodes that differ only in high bits.
  • Why power-of-two capacity? So h & (n-1) replaces the slower modulo, and resize can split each bucket into exactly two ("lo/hi") without rehashing every key.
  • Why load factor 0.75? Space/time compromise: keeps expected bucket length ~constant so lookup stays O(1) amortized.
  • Why treeify at 8 (Java 8+)? Under a decent hash, chain length 8 is astronomically improbable (Poisson ~1e-8) — so a long chain means a bad or adversarial hash; converting to a red-black tree bounds worst-case lookup at O(log n) (DoS protection).
  • null: one null key allowed (hash treated as 0 → bucket 0); many null values allowed.
HashMap is a power-of-two bucket array; put spreads the hashCode, indexes with a bit-mask, resolves collisions by chaining, treeifies a bucket past 8 nodes to cap worst case at O(log n), and doubles capacity past the 0.75 load factor.

2.4 equals()/hashCode() contract HIGH

The contract: equal objects MUST have equal hashCodes (the reverse is not required). Break it and hash-based collections silently corrupt: an object stored under one bucket can never be found again if its hashCode changed, and "duplicate" keys appear.

Mutating a key after insertion has the same effect — the entry is stranded in the old bucket. Keys should be immutable (records are perfect).

equals-equal implies hashCode-equal; violate it — or mutate a key's fields after insertion — and the entry becomes unreachable in its bucket, so I use immutable keys, ideally records.

2.5 Fail-fast vs fail-safe iteration HIGH

Mechanism: ArrayList/HashMap keep a modCount; the iterator snapshots it at creation and compares on every next() — mismatch → ConcurrentModificationException. It's best-effort debugging aid, not a thread-safety guarantee (and it fires even single-threaded if you structurally modify during a for-each).

Fail-safe: CopyOnWriteArrayList iterates a snapshot array; ConcurrentHashMap iterators are weakly consistent (no CME, may or may not see concurrent updates).

Fail-fast is a modCount check inside the iterator — a debugging aid that also fires single-threaded; to remove while iterating I use iterator.remove() or removeIf().

2.6 ConcurrentHashMap — how it actually scales HIGH

Java 8+ mechanism (the segment/stripe-lock story is Java 7 — outdated): CHM uses a Node table like HashMap; an insert into an empty bucket is a lock-free CAS; an insert into a non-empty bucket synchronizes only on that bucket's head node; reads are entirely lock-free (volatile reads). Resizing is cooperative — multiple threads help transfer buckets. size() is an estimate summed from striped counters (LongAdder-style).

Contract difference: no null keys or values (a null get would be ambiguous under concurrency). Compound safety comes from atomic methods: computeIfAbsent, merge, putIfAbsent — not from wrapping check-then-act in your own code.

Since Java 8 CHM does CAS for empty buckets and per-bucket synchronized for collisions with lock-free reads — and I get atomicity from computeIfAbsent/merge, never from external check-then-act.

2.7 Sorted & ordered maps/sets know it

TreeMap/TreeSet: red-black tree, O(log n), sorted by Comparable/Comparator — the comparator, not equals, defines uniqueness (inconsistent-with-equals comparators cause "disappearing" elements). LinkedHashMap: HashMap + doubly-linked list through entries — insertion order, or access order with the 3-arg constructor, which plus removeEldestEntry gives you a 5-line LRU cache (classic interview task).

TreeMap trades O(1) for O(log n) to get sorted order and range queries; LinkedHashMap in access-order mode is the standard LRU-cache building block.

3. Clean Code Examples

3.1 A correct hash key (record) vs a mutable key

Idiomatic (Java 17) 
record PointKey(int x, int y) {}   // equals+hashCode generated, immutable

var map = new HashMap<PointKey, String>();
map.put(new PointKey(1, 2), "A");
System.out.println(map.get(new PointKey(1, 2))); // A
Common wrong way 
class MutableKey { int x;  /* equals/hashCode use x */ }

MutableKey k = new MutableKey(); k.x = 1;
map.put(k, "A");
k.x = 99;                       // key mutated AFTER insertion
map.get(k);                     // null — hashes to a different bucket
map.containsKey(k);             // false, yet size() == 1 → leaked entry

Why it fails: the bucket index was computed from the old hashCode at put-time; lookups now search the wrong bucket. The entry is unreachable but still referenced → memory leak.

3.2 Removing while iterating

Idiomatic 
users.removeIf(u -> u.isInactive());          // best

// or, when you need the iterator anyway:
for (var it = users.iterator(); it.hasNext(); ) {
    if (it.next().isInactive()) it.remove();  // updates modCount safely
}
Common wrong way 
for (User u : users) {
    if (u.isInactive()) users.remove(u);  // ConcurrentModificationException
}

Why it fails: remove() bumps the list's modCount; the hidden iterator behind for-each detects the mismatch on the next next(). (Trap: removing the second-to-last element can exit without CME — hasNext() returns false early — which makes the bug intermittent.)

3.3 Atomic multi-map building

Idiomatic 
var byCity = new ConcurrentHashMap<String, List<User>>();
byCity.computeIfAbsent(u.city(), c -> new CopyOnWriteArrayList<>())
      .add(u);                                    // atomic bucket creation
Common wrong way 
List<User> list = byCity.get(u.city());   // check
if (list == null) {                        // ...then act: race window
    list = new ArrayList<>();
    byCity.put(u.city(), list);            // second thread's list is lost
}
list.add(u);                               // ArrayList also not thread-safe

Why it fails: two threads can both see null and both put — one list (with its data) is overwritten. Each individual call is thread-safe; the sequence is not.

3.4 Immutable collections (Java 9+)

Idiomatic 
List<String> roles = List.of("ADMIN", "USER");      // truly immutable
Map<String, Integer> limits = Map.of("api", 100);
List<String> copy = List.copyOf(mutableSource);      // defensive copy
Common wrong way 
List<String> view = Collections.unmodifiableList(source);
source.add("X");          // view now shows "X" — it's a live VIEW, not a copy
Arrays.asList(1, 2, 3).add(4);   // UnsupportedOperationException
                                  // (fixed-size view over the array, not immutable either)

Why it fails: unmodifiableList wraps, doesn't copy — mutations to the source leak through. Arrays.asList is a fixed-size adapter: set() works, add() throws. Also note List.of rejects nulls.

4. Tricks, Tips & Rules of Thumb

  • Default choice table: need order of insertion → ArrayList/LinkedHashMap; sorted → TreeMap; stack/queue → ArrayDeque (never Stack/LinkedList); concurrency → ConcurrentHashMap; read-mostly listener lists → CopyOnWriteArrayList.
  • Mnemonic "HAT-CLIC" for HashMap numbers: HashMap: capacity 16, load 0.75, Treeify 8 (un-treeify 6, min table 64), Capacity always power of two, Lookup O(1)→O(log n) worst, Index = hash & (n-1), Copy on resize (double).
  • Pre-size maps: new HashMap<>(expected / 0.75f + 1) — or Java 19+: HashMap.newHashMap(expected) — avoids rehash storms when loading bulk data.
  • hashCode of small ints/strings is deterministic per run — but iteration order of HashMap is unspecified; never assert on it in tests. If a test needs order, use LinkedHashMap.
  • Version gotchas: Java 8 added treeification + rewrote CHM (drop the "16 segments" answer). Java 9 added List.of/Map.of. Java 10+ var. Java 16 records. Java 21 adds SequencedCollection (getFirst()/getLast()/reversed() on List/Deque/LinkedHashMap) — mentioning it signals currency.
  • HashSet is a HashMap in disguise — it stores elements as keys with a shared dummy value object. Every HashSet question is a HashMap question.
  • String hashCode caching: String caches its hash (immutable), which is one reason Strings make cheap keys.
  • Streams tie-in: Collectors.toMap throws on duplicate keys — always supply the merge function in prod code: toMap(k, v, (a, b) -> b).

Top 5 questions with follow-up chains

  1. How does HashMap work internally?
    ↳ L1: Why is capacity a power of two? (bit-mask indexing + cheap resize split) ↳ L2: What changes during resize — does every key rehash? (no; each bucket splits into lo/hi by one bit)
  2. What happens if two keys have the same hashCode?
    ↳ L1: When does the bucket become a tree, and why 8? (Poisson argument, DoS hardening) ↳ L2: What must keys implement to treeify well? (Comparable; else identity-hash tie-breaking)
  3. Why must you override hashCode when you override equals?
    ↳ L1: What breaks in a HashSet if you don't? (duplicates stored, contains() false) ↳ L2: What if hashCode always returns 42 — is it correct? (contract-legal but degrades to one bucket → tree → O(log n))
  4. HashMap vs ConcurrentHashMap under concurrent writes?
    ↳ L1: What can actually go wrong with plain HashMap concurrently? (lost updates; infinite resize loop was Java 7 — Java 8 can still lose data/corrupt) ↳ L2: Why does CHM forbid null? (can't distinguish "absent" from "mapped to null" without racy containsKey)
  5. How do you remove elements while iterating a list?
    ↳ L1: Why does for-each throw CME? (hidden iterator + modCount) ↳ L2: Why might the buggy loop not throw sometimes? (removal of second-to-last element makes hasNext() false before the check)

6. Sticky-Note Summary

  • HashMap: spread(hash) → & (n-1) → chain → treeify at 8 (table ≥ 64) → resize at 0.75·capacity.
  • Power-of-two capacity = mask indexing + lo/hi bucket split on resize.
  • equals-equal ⇒ hashCode-equal. One direction. Keys must be immutable — use records.
  • Mutated/broken keys don't throw — they silently strand entries (leak + wrong lookups).
  • CME = modCount mismatch; single-threaded too; fix with removeIf / iterator.remove.
  • CHM (Java 8+): CAS empty bucket, per-bucket lock, lock-free reads, no nulls, atomic computeIfAbsent/merge.
  • ArrayList beats LinkedList in practice (cache locality); ArrayDeque for stack/queue.
  • List.of = immutable & null-hostile; unmodifiableList = live view; Arrays.asList = fixed-size adapter.
  • LinkedHashMap(accessOrder=true) + removeEldestEntry = instant LRU.
  • Java 21: SequencedCollection — getFirst/getLast/reversed across ordered collections.

Self-test (5 questions)

  1. A key's field used in hashCode is changed after put(). What do get(), containsKey(), and size() report, and why?
  2. Why does HashMap XOR the hashCode with itself shifted right 16 bits before indexing?
  3. Two threads call get-check-put on a ConcurrentHashMap to lazily create a value. Is that safe? What's the correct call?
  4. Exactly which conditions convert a HashMap bucket into a red-black tree?
  5. Why can the "remove inside for-each" bug sometimes complete without an exception?
Answers
  1. get/containsKey return null/false (lookup goes to the new hash's bucket; the entry sits in the old one); size() still counts it — a stranded, leaked entry.
  2. The index uses only the low log2(n) bits; XOR-ing the high 16 bits down mixes high-bit-only differences into the index, cutting collisions from poor hashCodes.
  3. Not safe — check-then-act is a race even on a thread-safe map; both threads can create and one value is lost. Use computeIfAbsent(key, fn), which is atomic and runs fn at most once per key.
  4. Chain length reaches 8 and table capacity is at least 64 (otherwise it resizes instead); the tree reverts to a list at 6 during resize.
  5. If the removed element is the second-to-last, size shrinks so the iterator's hasNext() returns false before the next modCount check — the loop just exits early, silently skipping the last element.
