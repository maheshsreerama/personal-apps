2. The Fundamentals

2.1 It's all servlet filters HIGH

Mechanism: the servlet container knows one filter: DelegatingFilterProxy (registered as "springSecurityFilterChain"). It delegates into the Spring context to FilterChainProxy, which picks the first SecurityFilterChain bean whose matcher fits the request and runs its ordered filters. Security happens before DispatcherServlet — before any controller exists.

    M --> C2[web chain: form login, session]
    C1 --> ORD[ordered filters: context load -> auth -> exception translation -> authorize]

Key ordered filters (know ~5, in order): SecurityContextHolderFilter (load context) → CsrfFilter → authentication filters (UsernamePasswordAuthenticationFilter, BearerTokenAuthenticationFilter/your JWT filter, BasicAuthenticationFilter) → ExceptionTranslationFilter → AuthorizationFilter (last: decides allow/deny).

Spring Security is a chain of servlet filters ahead of DispatcherServlet: DelegatingFilterProxy bridges into FilterChainProxy, which selects a SecurityFilterChain per request; authentication filters run early, AuthorizationFilter decides last.

2.2 Authentication model HIGH

The objects: an Authentication token starts unauthenticated (credentials only) and is submitted to the AuthenticationManager (impl: ProviderManager), which polls its AuthenticationProviders for one that supports() the token type. DaoAuthenticationProvider loads a UserDetails via your UserDetailsService, verifies the password with the PasswordEncoder (BCrypt default — salted, slow on purpose), and returns an authenticated token carrying GrantedAuthoritys.

Where it lives: SecurityContextHolder — a ThreadLocal. That's why @Async/new threads lose the user (propagate with DelegatingSecurityContextExecutor or the inheritable strategy). In session apps the context is saved to the HTTP session between requests; in stateless APIs it's rebuilt from the token on every request.

Authentication is a strategy chain: ProviderManager asks providers; DaoAuthenticationProvider = UserDetailsService + PasswordEncoder; the result sits in a ThreadLocal SecurityContextHolder, which is exactly why new threads don't inherit the user.

2.3 Authorization model HIGH

URL level: authorizeHttpRequests rules are evaluated by AuthorizationFilter using AuthorizationManagers — first matching rule wins, so order specific → general. Method level: @PreAuthorize("hasRole('ADMIN')") etc. via @EnableMethodSecurity — implemented as an AOP proxy interceptor (same proxy rules as @Transactional: public methods, external calls only, self-invocation bypasses it!).

Role vs authority: a role IS an authority with the ROLE_ prefix. hasRole("ADMIN") checks authority ROLE_ADMIN; hasAuthority("ROLE_ADMIN") is identical. Mixing the two conventions is the classic 403-that-makes-no-sense.

401 vs 403: ExceptionTranslationFilter catches AccessDeniedException downstream: anonymous user → start authentication via AuthenticationEntryPoint (401 / redirect to login); authenticated but insufficient → AccessDeniedHandler (403).

URL rules are first-match-wins so I order specific to general; @PreAuthorize is proxy-based AOP with the same self-invocation caveat as @Transactional; and hasRole('X') just means authority ROLE_X.

2.4 Stateless APIs with JWT HIGH

Flow: login endpoint verifies credentials → issues a signed token (header.payload.signature; HMAC or RSA). Every request carries Authorization: Bearer <jwt>; a filter (Boot's resource-server BearerTokenAuthenticationFilter with spring-boot-starter-oauth2-resource-server, or a custom OncePerRequestFilter) validates signature + expiry, builds an Authentication, sets it in the context. SessionCreationPolicy.STATELESS stops session creation; CSRF is disabled because there's no cookie-bound session for a cross-site request to ride (valid only while the token is NOT stored in a cookie sent automatically).

The honest trade-offs (interviewers probe these): the signature guarantees integrity, not secrecy — payload is only Base64, don't put secrets in it. Logout/revocation is unsolved by design: a signed token stays valid until expiry — mitigate with short-lived access tokens + refresh-token rotation, or a denylist (which quietly reintroduces state).

JWT auth is a per-request filter that verifies the signature and rebuilds the SecurityContext — no session; the costs are no built-in revocation and a Base64-readable payload, so short expiry plus refresh rotation is the standard design.

2.5 CSRF and CORS — different threats HIGH

CSRF attacks the server exploiting cookies being auto-attached: evil.com auto-submits a POST to yourbank.com and the browser adds the session cookie. Defense: synchronizer token the attacker can't read (CsrfFilter compares). Needed only for cookie/session auth; irrelevant for Bearer-header APIs (the attacker's page can't add your header). CORS is the browser protecting the user: it blocks cross-origin JS from reading responses unless the server opts in via Access-Control-Allow-Origin (preflight OPTIONS for non-simple requests). CORS is not access control — curl ignores it entirely.

CSRF exploits auto-attached cookies, so token-in-header APIs can disable it; CORS is a browser-enforced read-permission handshake, not a server-side security control — curl never sees it.

2.6 Password storage know it

BCrypt (default via PasswordEncoderFactories): per-password random salt embedded in the hash, tunable cost factor to stay slow as hardware improves. {bcrypt}-prefixed DelegatingPasswordEncoder allows migrating algorithms without breaking old hashes. Never MD5/SHA-256-alone (fast = brute-forceable), never reversible encryption.

BCrypt is deliberately slow and per-password salted; the {id} prefix in DelegatingPasswordEncoder lets you migrate algorithms hash-by-hash.

3. Clean Code Examples

3.1 Boot 3 SecurityFilterChain (the modern config)

Idiomatic (Boot 3 / Security 6.1+) 
@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http, JwtAuthFilter jwtFilter) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                 // stateless bearer API only!
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**", "/actuator/health").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")   // specific first
                .anyRequest().authenticated())                        // general last
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }
}
Common wrong ways 
// 1. Boot 2 style — REMOVED in Security 6:
public class SecurityConfig extends WebSecurityConfigurerAdapter { ... }

// 2. Rule order inverted:
.authorizeHttpRequests(auth -> auth
    .anyRequest().authenticated()                 // matches EVERYTHING first
    .requestMatchers("/api/auth/**").permitAll()) // dead rule → login returns 401

// 3. csrf.disable() copy-pasted into a session/cookie app → CSRF wide open

Why they fail: (1) WebSecurityConfigurerAdapter is gone in Spring Security 6 — component-style beans are mandatory. (2) First-match-wins: the permitAll rule is unreachable. (3) Disabling CSRF is only sound when no auto-attached credential (session cookie) exists.

3.2 A correct custom JWT filter

Idiomatic 
@Component
public class JwtAuthFilter extends OncePerRequestFilter {
    private final JwtService jwt;               // your parse/verify wrapper
    JwtAuthFilter(JwtService jwt) { this.jwt = jwt; }

    @Override
    protected void doFilterInternal(HttpServletRequest req,   // jakarta.servlet!
            HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String h = req.getHeader("Authorization");
        if (h != null && h.startsWith("Bearer ")) {
            var user = jwt.verifyAndLoad(h.substring(7));     // sig + expiry
            if (user != null) {
                var auth = new UsernamePasswordAuthenticationToken(
                        user, null, user.getAuthorities());   // authenticated ctor
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        }
        chain.doFilter(req, res);   // ALWAYS continue — authorization decides later
    }
}
Common wrong way 
if (h == null) { res.sendError(401); return; }  // filter rejects everything
                                                 // → /api/auth/login also 401!

Why it fails: the filter's job is only to populate the context when a valid token exists; rejecting must be left to AuthorizationFilter, otherwise permitAll endpoints die. Also: extending OncePerRequestFilter avoids double execution on forwards/errors.

3.3 Method security

Idiomatic 
@Service
public class AccountService {
    @PreAuthorize("hasRole('ADMIN') or #ownerId == authentication.name")
    public Account view(String ownerId) { ... }   // data-aware rule via SpEL
}
Common wrong way 
public Account viewAll() {
    return this.view("x");   // self-invocation: @PreAuthorize NOT evaluated
}
// and: @PreAuthorize("hasRole('ROLE_ADMIN')") → checks ROLE_ROLE_ADMIN → always 403

Why it fails: method security is proxy AOP — internal calls bypass it (same as @Transactional). And hasRole auto-prefixes ROLE_, so writing the prefix doubles it.

3.4 Getting the current user

Idiomatic (controller) 
@GetMapping("/me")
public UserDto me(@AuthenticationPrincipal UserDetails user) {  // injected
    return UserDto.from(user);
}
Common wrong way 
@Async
public void notifyUser() {
    var auth = SecurityContextHolder.getContext().getAuthentication();
    auth.getName();   // NullPointerException — new thread, empty ThreadLocal
}

Why it fails: the context is a ThreadLocal; @Async runs on a pool thread that never had it set. Pass the username as a parameter, or configure a DelegatingSecurityContextTaskExecutor.

4. Tricks, Tips & Rules of Thumb

  • Mnemonic "Who → May → Do": authentication filters decide who (early in chain), AuthorizationFilter decides may (last), controller does the do.
  • 401 = who are you (authentication missing/failed); 403 = I know you, no (authorization). Wrong one from your API usually means your EntryPoint/AccessDeniedHandler config.
  • Rule order: specific matchers before anyRequest() — always. Boot won't warn about dead rules (adding a matcher after anyRequest() does throw in recent versions).
  • Never put permitAll on actuator wildcards in prod — /actuator/health only; heapdump/env leak secrets.
  • Defense in depth: URL rules for coarse gates + method security on services for the real invariants — URL rules silently stop protecting a method the day someone adds a second controller path to it.
  • Testing: @WithMockUser(roles = "ADMIN") + MockMvc; spring-security-test's jwt() post-processor for resource servers. Test 403s, not just 200s.
  • Version gotchas: Boot 3/Security 6: WebSecurityConfigurerAdapter and authorizeRequests()/antMatchers() are gone — use SecurityFilterChain beans, authorizeHttpRequests(), requestMatchers(); lambda-DSL is mandatory in 6.1+ (chained non-lambda style removed); @EnableGlobalMethodSecurity → @EnableMethodSecurity (prePostEnabled now default true); everything servlet is jakarta.servlet.
  • Filter registration trap: a filter that's a @Component AND added via addFilterBefore can run twice (Boot registers @Component Filters with the container too) — mark it with a FilterRegistrationBean disabled, or don't make it a bean picked up both ways.

Top 5 questions with follow-up chains

  1. Walk a request through Spring Security.
    ↳ L1: Where do multiple filter chains come in? (FilterChainProxy picks first matching chain — e.g. /api/** stateless vs web form-login) ↳ L2: Which filter makes the final allow/deny call and when? (AuthorizationFilter, last, after authn filters populated the context)
  2. How would you secure a stateless REST API?
    ↳ L1: Why is CSRF safe to disable here? (no auto-attached credential; breaks if you move the JWT into an auto-sent cookie) ↳ L2: How do you handle token revocation/logout? (short-lived access + rotating refresh tokens; denylist if hard revocation is mandated)
  3. How does login actually verify a password?
    ↳ L1: Why BCrypt over SHA-256? (adaptive cost + salt vs fast hash) ↳ L2: How do you migrate 1M legacy SHA-1 hashes without a reset? (DelegatingPasswordEncoder id-prefix; re-encode on successful login)
  4. Difference between securing URLs and securing methods?
    ↳ L1: Which wins if both apply? (both run — URL first at filter level, then method interceptor; either can deny) ↳ L2: Why can @PreAuthorize silently not run? (self-invocation / non-public method — proxy AOP)
  5. Your endpoint returns 403 though the user has ADMIN. Debug it.
    ↳ L1: First checks? (authorities actually on the token — ROLE_ prefix mismatch; rule order; which filter chain matched) ↳ L2: What logging flips the black box open? (logging.level.org.springframework.security=TRACE shows chain selection and the authorization decision)

6. Sticky-Note Summary

  • Filters, not interceptors: DelegatingFilterProxy → FilterChainProxy → matched SecurityFilterChain → DispatcherServlet.
  • Authn = who (401, AuthenticationEntryPoint); Authz = may (403, AccessDeniedHandler).
  • ProviderManager → DaoAuthenticationProvider = UserDetailsService + PasswordEncoder (BCrypt).
  • SecurityContextHolder is a ThreadLocal — async/new threads are anonymous unless delegated.
  • URL rules: first match wins; specific before anyRequest().
  • hasRole("X") == hasAuthority("ROLE_X"). Never write ROLE_ inside hasRole.
  • JWT: signed, readable, irrevocable until expiry → short TTL + refresh rotation; STATELESS session policy.
  • CSRF: cookie-riding attack — disable only for header-token APIs. CORS: browser read-permission, not security.
  • @PreAuthorize = proxy AOP → public methods, external calls (same trap family as @Transactional).
  • Boot 3: SecurityFilterChain beans + authorizeHttpRequests/requestMatchers; the Adapter and antMatchers are gone; jakarta.* everywhere.

Self-test (5 questions)

  1. A request hits /api/admin/users with a valid JWT lacking ROLE_ADMIN. Trace which filters touch it and where 403 is produced.
  2. Why does a permitAll login endpoint return 401 when a naive JWT filter is installed — and what's the correct filter behavior?
  3. @PreAuthorize("hasRole('ROLE_MANAGER')") always denies a manager. Two distinct bugs could cause this — name both.
  4. Your SPA on app.example.com calls api.example.org and the browser blocks it. Is this CSRF or CORS, what fixes it, and does the fix weaken security for curl users?
  5. Session-cookie web app: which two config mistakes from the notes would open it to CSRF, and why is the same config fine for a Bearer-token API?
Answers
  1. The api chain matches; JWT/BearerToken filter validates the token and populates SecurityContextHolder; AuthorizationFilter (last) evaluates hasRole("ADMIN") → AccessDeniedException; ExceptionTranslationFilter sees an authenticated user → AccessDeniedHandler → 403 (not 401).
  2. The naive filter rejects requests without a token itself (sendError 401 + return) — so unauthenticated login calls die before authorization. Correct: on missing/invalid token just continue the chain without setting authentication; AuthorizationFilter will allow permitAll routes and deny the rest.
  3. (a) Double prefix: hasRole prepends ROLE_ → it checks ROLE_ROLE_MANAGER. (b) The user's authorities were stored without the ROLE_ prefix (e.g. "MANAGER") so even hasRole('MANAGER') fails until authorities are granted as ROLE_MANAGER or checked with hasAuthority.
  4. CORS — different origin (host differs), browser preflights and blocks reads. Fix: server allows the origin via CorsConfigurationSource wired into http.cors(). No — curl was never restricted; CORS only governs browsers, so allowing an origin doesn't change non-browser access at all.
  5. csrf.disable() copy-pasted, and/or accepting state-changing GETs. With session cookies the browser auto-attaches credentials to attacker-initiated requests — the token check is the defense. A Bearer API is safe because the attacker's page cannot make the victim's browser add the Authorization header.
